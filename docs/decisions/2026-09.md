## 2026-09-10 — the Fleet page 500'd, twice, on an OPTIONAL lookup

**Operator, verbatim:** *"Why there are zeros in those 2 projects? didn't we intorduced loki also
there? if not then what is the value? we need to have full observability and full security like in
cybergod.ai for all our projects otherwise we will end up like with the jobhuntwow cyber security
issue"* — and then, after the first fix: *"Your last version destroyed the fleet status
comletely."*

### What he was looking at

klimaanlage-preise.de and s4biz.io rendered `0 requests · 0 attack-shaped · 0 visitors · 0 alerts`
on Admin -> Fleet while both were plainly serving traffic. Every count on that page came from a
FILE — the shared events log that colt-web mounts. Those two projects write to `polara_events` and
`s4biz_events`, volumes this container does not mount and must not: an `external:` volume reference
is what made colt-web undeployable on staging, and a status page is never worth coupling a deploy.

The cosmetics were the smaller half. `watch()` — the loop that applies cybergod's OWN detector and
its OWN Telegram credentials to every other project — reads through the SAME function. So klima and
s4biz could not page the operator about a scanner at all. That is not a smaller version of
cybergod's security. It is none of it, and it is the jobhuntwow shape exactly.

### The fix, and the substrate it rests on

Both projects' promtails already push to `videodead-loki-1`, the same Loki as everything else on
the box. `perseus_client` prints its telemetry to stdout, so those `evt=http` lines have been in
Loki the whole time. Reading them needs no volume mount and therefore carries none of the deploy
coupling.

`_loki_fetch(line_filter, start_ts, limit) -> (rows, answered)` became the ONE query
implementation, used by the heartbeat lookup and the traffic lookup, so the badge and the numbers
beside it cannot disagree about which Loki they asked. **`answered` is not `len(rows)`** — "Loki
says this project sent nothing" and "Loki never answered" are different facts and the second must
never render as a zero.

Two things stated rather than discovered later:

- **DEDUPE.** One request produces TWO stdout lines: the project's own telemetry and the sidecar's
  `observe()`. The key is `(evt, ts, ip, method, path)`. `ts` is whole seconds, so two identical
  requests from one address inside one second collapse into one — a bounded UNDERCOUNT, in the
  noisiest direction only.
- **PARTIAL.** The fetch is capped. A project that really exceeds the cap is reported as a FLOOR
  ("at least N"), never as a confident, wrong, too-small total.

### The outage: `Could not read the fleet status.`

Two defects, both mine, both violations of rules already written in the file above the code.

1. **Parsing sat OUTSIDE the `try`.** An unexpected envelope (`doc` not a dict) raised
   `AttributeError` straight out of `_loki_fetch`, past every caller, into a 500. An OPTIONAL
   lookup was able to take the whole page down. The parse now lives inside the `try`, and `rows` is
   bound before it, because a name whose binding depends on which branch of a `try` ran is one edit
   away from a `NameError` — which here is another 500.

2. **The request path BLOCKED on Loki.** Two own-log projects x three candidate selectors x a 3s
   timeout, on 24-hour / thousand-line queries instead of the heartbeat's 15-minute / 200-line one:
   up to eighteen seconds on a cold cache. The comment on the beat cache four functions up had
   already written the rule — *a status page that hangs is its own outage* — and the change ignored
   it. That is defect class 33 against my own file, in the same file.

   `status()` now only ever READS a cache. A daemon thread fills it (`_loki_events_async`, one
   refresh in flight, guarded by a `busy` flag); the background alerting loop passes `block=True`,
   because it runs every 300s in an executor and has the time the page does not — and an alert
   computed from an empty cache is not a quiet project, it is a scanner nobody was told about.
   A cold cache renders `elsewhere` for one page load and the numbers appear on the next.

`PERSEUS_LOKI_EVENTS=0` is a kill switch, added because the only way back from the first version
was a redeploy.

### The third defect, found while fixing the second

`status()` read the cache TWICE — once through `_tail_events` for the counts, once directly to
decide which projects Loki had answered for. A background refresh landing between the two reads
would badge a project `live` while its numbers came from the older, emptier snapshot: `live` beside
0 requests, a confident wrong number, worse than the honest `elsewhere` it replaced. One read is
taken first and handed down (`_tail_events(loki_rows=...)`), and the test asserts the READ COUNT,
which is deterministic, instead of racing the thread.

### Tests

`test_the_page_never_waits_on_loki` fails if any traffic query is issued on the request thread; the
heartbeat query is exempt BY URL rather than by silence, because it is the small bounded one that
was always inline and never hung. `_rows_after_refresh()` primes the cache synchronously, so no
count assertion depends on a daemon thread finishing — a test that does is a coin flip that teaches
the operator to re-run a suite rather than read it.

**Rules earned:** an optional lookup may make a page more accurate, never less, and never slower
than the page's own budget; and `answered` is not `len(rows)`.

## 2026-09-10 — the rollout excluded the project that renders the page

**Operator:** *"i still see 2 are missing"*, then *"there is a progress but still not complete I do
not understand what seems to be the problem with nailing those two items at once?"*

`perseus.py --rollout` deployed five projects and reported `5 deployed / 0 failed`, and klima and
s4biz still rendered `elsewhere / not installed`. Cause: cybergod itself was not in `ROLLOUT`, and
cybergod is the project that SERVES the Fleet page — so the fixed `fleet.py` was never deployed.

The comment justifying the exclusion claimed that including cybergod "would recurse". That claim
was FALSE and was disproved by grepping `ship.py`, which calls `perseus.py --clients` and
`--install-only` and never `--rollout`. It cost the operator two rounds. `cybergod.ai (the Fleet
page itself)` is now the LAST entry in `ROLLOUT`, and
`test_ship_py_never_invokes_the_rollout_which_is_the_real_recursion_guard` asserts the actual guard
instead of a comment. The test that encoded the old doctrine was rewritten with its old reasoning
kept in the docstring, per defect class 17.

The diagnosis came from the badge STRING, not from inference: `not installed` is a string the
current `fleet.py` cannot produce, so the running code was old. **Read what the page printed, not
what the deploy log claimed.**

## 2026-09-09 — CLAUDE.md was costing ~160,000 tokens per turn

**Operator:** *"can you please change the claude.md file like you mention in order to fix the `This
conversation is too long to continue. Start a new session, or remove some tools to free up space.`"*

CLAUDE.md had reached 646 KB / 7,950 lines / 307 sections and is re-injected on EVERY turn, so it
spent ~160k tokens before the operator typed anything. That is the error, in full.

`docs_split.py` writes the current file byte-for-byte into `docs/decisions/HISTORY-*.md`, VERIFIES
the copy ends with the original exactly, refuses to touch anything if it does not, and only then
MOVES `docs/CLAUDE.core.md` into place. A move, not a copy: two files holding the same doctrine is
the "one value, several homes" defect this repository has paid for more than any other, and the
newer home always loses.

Measured: `636.3 KB / ~162,894 tokens` -> `34.3 KB / ~8,778 tokens`; history 652,499 bytes.

The lean file was written by hand, never generated. Deciding which doctrine must hold on every turn
is a judgement, not a transform, and a script that guessed would quietly drop a rule.

`tests/test_claude_md_size.py` fails the build if it grows back. It imports the budget from
`docs_split.BUDGET` by PATH, and it also asserts `size > 5_000` — a size test that an empty or
truncated file could pass is not a check.
