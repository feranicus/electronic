# Roles on cybergod.ai — 22 November 2026

## What was asked for

> some sort of KISS RBAC to our users on the website www.cybergod.ai — for example for now I'm only
> the admin user but there are old colt and some other users that I can't remove from system and we
> need to assign roles such as admin, Sales Rep, Presale, S4biz Power user, Company Admin (he can
> create sub users for same company users like admin but only for that company like Colt for
> example), Reseller that can also create sub company users

The phrase that decides the design is **"users that I can't remove from system"**. Those are the
addresses on the administration page with no Remove button: `armin.hall@colt.net`,
`emanuel.pradera@colt.net`, `frank.oldenburg@abakus-tk.de`. They have no account here at all. They
reach the platform because `colt_auth.EMAIL_RE` admits `name.familyname@colt.net`, and they sign in
with the shared `COLT_BOT_PASSWORD`. There is nothing to delete, which is why the button is absent.

## The model, and where it comes from

The same three things every platform that sells through a channel converges on, and no more:

* a **tenant** — here the email domain, because `colt_auth.PARTNER_DOMAINS` already decides trust
  that way and inventing a second notion of "company" would give one fact two homes;
* a **membership** with one **role**;
* a role that is a named **bundle of permissions**, never a list of screens.

SecurityScorecard, Bitsight and Pipedrive all let a customer administer their own users without
ever seeing another customer's, and all three make "can create users" a permission some roles hold
and others do not. Seven roles, thirteen verbs, ordered by seniority; `roles.py` prints the matrix
(`python roles.py`) so the policy can be read rather than inferred.

A permission is a VERB — `assess.run`, not "can see the Assess tab". `_require_perm("…")` is a
FastAPI dependency, and an unknown verb answers NO, so a typo in a decorator closes a route instead
of opening one.

## The defect that shaped it

The first version put a `role` column on the `users` table. It shipped on 22 Nov and was never
written to, which is the only reason this is a design note rather than an incident.

`users.pw_hash` is `NOT NULL`. A role for a shared-password user therefore meant inventing a
credential row, and that row has two side effects nobody asked for:

1. `user_store.has_account()` starts returning True for them. That function exists to decide
   whether the shared fallback password still applies — "a disabled user must not fall back to the
   shared password and get in anyway". So **assigning a role would have locked the person out.**
2. `colt_auth._has_enabled_account()` starts treating the row as an authorisation source in its own
   right, which is correct for an administrator who deliberately created an account and wrong for a
   side effect of naming somebody a Sales Rep.

Roles live in `user_roles(email PRIMARY KEY, role, updated_ts, set_by)`. `users` answers "how does
this person prove who they are"; `user_roles` answers "what may they do". The dead column stays
because the droplet has it and a schema that differs between boxes is its own class of bug;
`tests/test_roles.py::test_nothing_reads_the_dead_role_column` parses every SQL statement in
`user_store.py` and fails the build if one touches it again. (The first version of that check
grepped for `SET role=` and failed on the correct code, because the legitimate `user_roles` upsert
contains the same substring — class 4, assert the property, not a string the right answer contains.)

## The second defect, found by a request-path test

With the store fixed, `POST /api/admin/users/<who>/role` returned 200, the row was written, and the
person **disappeared from the page**. `admin_users()` builds its list from credential rows plus
everyone in `AUTH.authed` — people who have signed in *since this process started*. Somebody with
only a role row is in neither, so the role could never be seen or changed back.

This was invisible to every AST test in the file and obvious the moment a real request was issued.
Class 9 again: the policy was correct and the screen could not show it.

## Who may grant what

`may_grant()` is strictly downward and refuses equal rank too: a company administrator minting a
second company administrator is how one compromised account becomes two, and the platform
administrator can always do it. `may_touch()` confines a role holding `users.invite.org` to its own
tenant — that single rule is what keeps one customer out of another customer's user list.

Two refusals belong to the route rather than to the policy, and both are about recovery:

* **nobody edits their own role.** An administrator who is not on the committed `ADMIN_EMAILS`
  floor could otherwise demote themselves out of the page that would undo it.
* **the committed floor is not editable here.** `colt_auth.ADMIN_EMAILS` wins over any stored row,
  so writing one would store a value the server then ignores and display a role nobody is being
  given.

## The doctrine that had to be corrected

`tests/test_admin_users.py::test_every_admin_route_is_gated_server_side` asserted that every
`/api/admin/*` route calls `_require_admin`. The role route does not: it authenticates with
`_require_ready` and then asks `may_grant` + `may_touch`, which is strictly narrower (a platform
administrator passes both) and is what lets a company administrator reach it later without a code
change to the rule. Writing `_require_admin` there as well would make the policy decoration.

The test now carries a NAMED exception, one route at a time, and the exception must demonstrate its
alternative — the route is asserted to call both policy functions, and a stale entry that no longer
matches any route fails the build rather than quietly becoming a blanket hole. The original
reasoning is kept above it, because deleting it loses why.

## What was proved

Ten mutations, ten caught, every file restored byte-for-byte and hashed before and after:

| mutation | caught by |
|---|---|
| `set_role` accepts an undefined role | the store test |
| `set_role` writes a credential row instead of a role row | three tests, including the lock-out assertion |
| the route drops the self-edit refusal | the route test |
| the route stops asking `may_touch` | the route test |
| the route stops asking `may_grant` | five tests |
| the committed-floor refusal is dropped | the route test |
| the listing stops merging role-only people | the request-path test |
| the listing reports the stored value instead of the effective role | the listing test |
| a role loses its label in the picker | the derived-label test |
| German loses one role label | the derived-label test |

The fixture for the central test asserts its own condition first (`assert not us.has_account(who)`)
— without that it would be testing a credential user and passing for the wrong reason.

## The second pass: committing a change, and seeing what a role means (22 Nov, same day)

Three things were wrong with the first version, and all three were about the operator rather than
the policy.

**The picker saved on `change`.** A mis-click was a silent privilege change with nothing on screen
to say so. There is now a PENDING value per address and an **Apply** button beside the control,
enabled only when there is something to commit - so the button's own state answers "did my choice
register?". The confirmation names the address and the role ("armin.hall@colt.net is now Sales
representative"), because a message reading "Saved" is indistinguishable from the confirmation of
the previous click, which is class 26 wearing different clothes.

**A new account could not be given a role at birth.** You had to create it, then find its row. The
create form carries a role now, offering only what `grantable` allows, and the same request applies
it. If the grant is refused the account still exists - its password was issued and shown once - so
the response reports BOTH: created, and the role was not applied, with the reason. Reporting one
and not the other is a lie by omission the administrator only discovers when the person cannot do
their job.

**A role name is a label, and nobody could see behind it.** The page now renders the permission
matrix - every role, its verbs, and what each verb allows - read from `roles.py` over the API. Not
copied into the frontend: a second description would drift from the policy the first time a verb
was added, and the drift would be invisible until somebody was refused something the screen said
they had. A test asserts no verb string appears in `Admin.jsx` at all.

The decision itself moved into `_grant_role()`, because two screens now need the same answer and
an authorisation question answered in two places is how the weaker screen becomes the one that
gets used. Both test files had to follow it: a test that kept reading the route body would have
reported the guards missing from code that has them (class 4 - resolve the call site).

The create row gained a fourth field, so the width was worked out rather than eyeballed: four
flexible `.fld`s would need 4x240 + 48 + 96 = 1104px before wrapping, wider than the card. The
role control is a select with short options, so it takes a fixed 220px like `.fld-lang` already
does - 3x240 + 220 + 48 + 96 = 1084px.

Eight mutations, eight caught, including the two that matter most: the picker writing on change
again, and a refused role on create being swallowed.

## What is not built yet

The page itself is still `_require_admin`, so only a platform administrator can open it. Letting a
company administrator in means giving `admin_users()` a tenant-scoped listing; the policy for it
already exists and is tested. The pipeline feature asked for in the same message is next, and drops
in behind `_require_perm("pipeline.view")`.
